Why I Built This

While researching niche content markets with Google Keyword Planner, I discovered that "dark romance books" and related keywords have 100K–1M monthly searches with +900% year-over-year growth and consistently low competition. This was a clear signal: massive demand, underserved by existing tools.

I decided to build DarkRomanceBooks.ai — an AI-powered book discovery engine that solves a real problem for readers: finding the right dark romance book by trope, mood, and taste. The project is designed as a solo full-stack system that runs autonomously — every search creates new content, every new page attracts more organic traffic, creating a self-sustaining growth flywheel.

AI / LLM Integration

Search Recommendations

  • Model: gpt-5-search-api via Chat Completions API
  • Built-in web search tool for real-time book data
  • Structured JSON output: title, author, description, tropes, rating, URL
  • Language detection: ASCII-only queries → English response
  • Auto-retry with exponential backoff (3 attempts, 5s/10s/15s)
  • Citation stripping: removes markdown links, 【】 brackets
  • Deduplication by title+author key

Editorial Content Generation

  • Model: gpt-4o-mini with web_search tool
  • Searches real reader reviews before writing
  • 200-250 word reviews, exactly 3 paragraphs
  • Graceful fallback: responds "SKIP" if book info unreliable
  • Batch processing with 1s delay between requests
  • Post-processing: stripCitations() preserves paragraph breaks

Author Profile Generation

  • Model: gpt-4o-mini — optimized for structured JSON output
  • Generates bio, style tags, notable works, reader sentiment, related authors
  • Author photos fetched from Open Library API by author name search
  • Slug-based matching groups books by author despite name variations
  • Name normalization: "H. D. Carlton" → "H.D. Carlton"
  • Daily cron discovers new authors from book table and generates profiles

Book Description Backfill

  • Model: gpt-4o with explicit web_search tool
  • Searches the web for each book, generates 50–80 word blurbs
  • Post-processing: strips preambles, citations, markdown, truncates to 3 sentences
  • Responds "SKIP" if reliable info unavailable — avoids hallucinated descriptions
  • One-time batch script + ongoing cron enrichment for new books

Two API Call Paths

  • Chat Completions API — for *-search-api and *-search-preview models
  • Responses API — for gpt-4o-mini / gpt-4o with explicit web_search tool
  • Unified RawSearchResponse interface normalizes both formats
  • Runtime model detection: isChatSearchModel() switches path
  • Configurable via OPENAI_MODEL env variable

Multi-Source Data Enrichment

Books are enriched with structured data from three external sources — Open Library, Google Books, and Kaggle datasets — giving each book page rich metadata, real reader ratings, and review excerpts without relying on any single API.

Open Library API

  • Ratings — Average score, total count, 1–5 star distribution
  • Bookshelves — Want-to-read, currently-reading, already-read counts
  • Series info — Series name and position (e.g. "#2 in The Mindf*ck Series")
  • Work keys — Stable identifiers for cross-referencing editions
  • ISBN resolution — ISBN-13 for structured data and affiliate links
  • Title cleaning pipeline strips parenthetical series info for better API matching

Google Books API

  • Descriptions — Publisher blurbs as fallback for AI-generated content
  • Ratings — Average rating and ratings count (cross-validated with OL)
  • Page counts — For reader activity display
  • Categories — Genre tags for filtering and SEO
  • Published dates — Original publication year
  • ISBNs — ISBN-10 and ISBN-13 extraction from industry identifiers

Kaggle Datasets

  • Kindle metadata — kindle_data-v2.csv (36MB): ASIN, Kindle price, star distribution, review counts
  • Goodreads reviews — scraped.csv: Romance-specific review text and scores
  • Title + author fuzzy matching against existing book database
  • Batch import with duplicate detection via composite keys
  • Stored in dedicated BookReview table with source tracking

Enrichment Pipeline

  • Batch script — enrich-books.ts processes all books with OL + Google Books APIs
  • Import script — import-kaggle-reviews.ts loads CSV review data
  • Auto-enrichment — Cron job enriches new books on each daily sync
  • Rate limiting — 1s delays between API calls to respect external limits
  • Incremental — Tracks enrichedAt timestamp, skips already-enriched books
  • 14 new fields on Book model + full BookReview table

Challenges & Technical Decisions

Real engineering problems I encountered during development, and how I solved them.

Problem

Persistent 404s on New Book Pages

Users searched for a book, clicked the result, and got a 404. The book hadn't been saved to the DB yet because saveSearchBooksToDb ran in an after() callback — asynchronous and non-blocking.

Solution

Moved book saving to be synchronous before the response. Added a self-healing fallback: if a book isn't in the DB, the page checks SearchResultCache and creates the entry on-the-fly. Reduced ISR revalidation from 24h to 60s to prevent stale 404 caching.

Result

404 rate dropped to effectively zero. Book pages available instantly after search.

Problem

Google Books API Quota Exhaustion

Each search triggered ~100 Google Books API calls for cover images, burning through the 1,000/day free quota in minutes during testing.

Solution

Built a 3-layer cover cache: in-memory Map (500 entries, 1h TTL) → PostgreSQL BookCoverCache (30d TTL) → API fallback. Added Open Library as the primary source before Google Books. Batch endpoint with concurrency limit of 3.

Result

API calls reduced from ~100/search to ~3/search (97% reduction). Quota no longer an issue.

Problem

AI-Hallucinated Book URLs

GPT-5 returned Goodreads and Amazon URLs that looked real but were fabricated. Users clicked them and got "page not found" errors on external sites.

Solution

Never trust AI-generated URLs. All Goodreads links are now constructed as search queries (goodreads.com/search?q=...). Amazon links use a deterministic URL builder with the affiliate tag.

Result

100% link reliability. Every external link reaches a valid page.

Problem

SSR Search Path Missing Book Saves

The server-rendered search page (/search?q=...) used a direct function call that bypassed the API route. Books were only saved via the /api/search route, so SSR searches created no DB entries.

Solution

Extracted saveSearchBooksToDb into a shared module (lib/save-search-books.ts) and integrated it into both the API route and the SSR fetch path. Both now save books synchronously before returning results.

Result

Unified data pipeline. Books are saved regardless of how the user reaches the search results.

Problem

Choosing Between Sync vs Async Saves

Trade-off: Saving books inside after() is faster (response returns immediately) but causes 404s. Synchronous saving adds ~200ms latency but guarantees pages exist when clicked.

Decision

Chose synchronous saves for book data (critical path — user will click these links) and async after() for search logging (non-critical — analytics can be delayed). This balances UX reliability with response speed.

Result

+200ms search latency, but zero 404s and zero race conditions on book pages.

Problem

Dual OpenAI API Path Complexity

Different OpenAI models use different APIs: *-search-api uses Chat Completions, while gpt-4o-mini uses Responses API with explicit web_search tool. Switching models broke the parsing logic.

Solution

Built a model detection function (isChatSearchModel()) that switches API path at runtime. Both paths normalize to a unified RawSearchResponse interface. Model is configurable via a single env variable.

Result

Hot-swappable AI models with zero code changes. Just update OPENAI_MODEL env var.

Problem

Author Name Collisions & Dirty Data

The same author appeared with multiple name formats — "H.D. Carlton" vs "H. D. Carlton", "CJ Roberts" vs "C.J. Roberts". Scraped data included artifacts like "Black Rose, da Knight". Book-author associations broke across name variants.

Solution

Built a name normalization pipeline: normalizeAuthorName() standardizes initials and whitespace on write. Switched all book-author queries to slug-based matching (generateAuthorSlug()) so "H.D. Carlton" and "H. D. Carlton" resolve to the same hd-carlton slug. Ran a one-time cleanup to merge ~19 duplicate book pairs and normalize 300+ author names in-place.

Result

Consistent author profiles. All name variants correctly associated with the right books and author pages.

Problem

Open Library Title Matching Failures

Open Library search returned "not found" for ~60% of books. Titles in our database included parenthetical series information like "Legendborn (The Legendborn Cycle, #1)" which caused API queries to fail.

Solution

Built a title cleaning pipeline (cleanBookTitle()) that strips parenthetical series info, edition markers, and subtitle noise before API calls. Applied the same normalization in both the batch enrichment script and the Open Library client library.

Result

Match rate improved from ~40% to ~85%. Books with clean titles now reliably return ratings, bookshelves, and series data from Open Library.

Problem

Database Connection Pool Exhaustion

Batch operations (author cron processing 30+ authors, description backfill script) exceeded the Supabase connection pool limit (MaxClientsInSessionMode), causing 500 errors across the live site.

Solution

Switched batch processing to sequential single-slug execution with explicit connection cleanup. Added rate limiting between API calls (1–4s delays). Set connection_limit=3 in the Prisma pg adapter to stay within PgBouncer limits.

Result

Stable connection usage during batch operations. No more pool exhaustion affecting production traffic.
